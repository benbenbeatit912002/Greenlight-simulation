Climate upload and model-backed simulation design

2026-09-06 · Design assessment completed; implementation not started

User request and scope

Assess a public-facing project where users provide climate data in an Excel workbook, choose a simulation period, control greenhouse equipment and playback in the frontend, and observe greenhouse changes calculated by the GreenLight-Gym2 model. The user explicitly forbids modifications to both practice repositories.

Current implementation evidence

  • The simulator already has a GreenLight-Gym2 adapter and a separately labelled browser approximation. The adapter uses a 15-minute control interval, six normalized controls, and the 28-state model described in the project model card.
  • backend/greenlight_adapter.py selects fixed Amsterdam weather scenarios and passes a weather directory inside the configured external source checkout to the environment. No custom workbook input is implemented in the inspected API or frontend.
  • The UI already supports speed selection and start/pause behavior. A date-based run definition, validated uploaded weather, and persistent full-run replay would extend this foundation.
  • The adapter retains only 97 history records. Multi-day inspection needs a complete run record independent of the rolling chart window.
  • The adapter's insideRadiation is a simplified calculation from radiation, screens, and lighting, rather than a direct model observation. Other displayed derived values and units also need an explicit provenance audit before claiming that every value is a direct scientific-model output.
  • The model card correctly states that local integration is not independent validation of prediction accuracy for a user's greenhouse.

Recommended product definition

Build a weather-driven greenhouse scenario workbench: upload outdoor weather, inspect data quality, choose a documented greenhouse/crop configuration and period, run the scientific model, explore climate and actuator histories, and compare control strategies under the same conditions. Indoor observations belong in a separate optional validation dataset; they must not silently replace predicted indoor states.

Start with one reference tomato-greenhouse configuration and a 24- to 72-hour demonstration, subject to model initialization and weather coverage requirements. Greenhouse geometry, cover properties, equipment capacities, crop state, initialization, and calibration matter in addition to weather. Present early results as reference-greenhouse simulation, not a validated digital twin or guaranteed yield prediction.

Proposed workbook contract

The following is a proposed user-facing schema, not an implemented or final model input contract. Confirm compatibility with the exact local source revision before implementation.

InputMeaning and checks
Timestamp and timezoneReal dates, ordered unique records, explicit timezone/offset and daylight-saving handling; report gaps and sampling interval.
Outdoor air temperatureDegrees Celsius; finite numeric values and documented plausibility checks.
Outdoor relative humidityPercent, 0 to 100; do not interpret fractions as percentages without confirmed mapping.
Global solar radiationW/m2; distinguish global radiation from PAR and accumulated energy.
Outdoor wind speedm/s; nonnegative values and declared measurement context.
Additional weather and metadataSky temperature, soil temperature, outdoor CO2, site information, and any required derivation inputs. Missing quantities need a documented method and explicit assumption acknowledgement, or must block the run.

Accept a constrained .xlsx template first, preview column mappings and errors before execution, and impose upload/decompression/row limits. Do not execute macros or workbook formulas; required input cells should contain numeric values. Store uploaded data and generated results only inside the simulator and exclude private inputs from Git and static-file serving.

Model integration and time semantics

  • Implement parsing, unit conversion, weather provision, run storage, and API/UI changes exclusively in Greenlight-simulation. Keep the protected source immutable. Any later permitted source import must use Python -B and PYTHONDONTWRITEBYTECODE=1, with all writable paths directed inside the simulator.
  • Replace the assumption that weather must live alongside protected source. Supply uploaded weather through an adapter/provider or simulator-owned weather directory, following the exact supported source contract. Stop if compatibility requires modifying the protected repository.
  • Require sufficient weather coverage for the selected run, initialization and any controller look-ahead. Do not silently repeat weather, invent a following year, or extrapolate beyond coverage.
  • Distinguish weather sampling, model/control intervals, and screen playback speed. Faster playback must preserve the model's integration and control schedule rather than changing physical behavior.
  • Provide start/end date selection, play/pause, single-step and acceleration. Timeline scrubbing initially replays saved states; changing controls in the past starts a new calculation rather than pretending the model is reversible.
  • Uploaded-weather scientific runs must fail clearly when the full engine is unavailable. A browser-only demo may remain separately available, but must not silently replace the selected scientific engine.
  • Record model/source identity, parameters, weather checksum, timezone, initialization, seed, controls, timestep, derivations and output units with each run. Keep measured inputs, model states, derived indicators and illustrative graphics distinguishable.
  • For public reproducibility, document a pinned, legally distributable model installation path within the simulator. Other users should not require the owner's D-drive research checkout. Licensing and packaging need verification before any redistribution.

  5. Finish English setup documentation, a safe sample dataset/template, dependency/version and license documentation, and a fresh-install demonstration independent of the protected repositories.

Public-source research and limitations

The upstream weather component separates weather loading from scenario sampling. Its weather conversion implementation uses radiation, outdoor temperature, vapor pressure, CO2 density, wind, sky and soil temperature, plus derived daily/daylight quantities. It includes a fixed CO2 assumption and a Netherlands-specific soil-temperature function. These are upstream observations, not confirmation that the protected local fork is identical. They motivate explicit conversion and assumption records instead of treating arbitrary Excel columns as sufficient model inputs.
