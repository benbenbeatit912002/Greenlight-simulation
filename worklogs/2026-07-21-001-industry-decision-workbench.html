Product decision

The recommended side project is an explainable, pre-deployment greenhouse decision-support workbench. Its first user is a greenhouse-control student, researcher, technical adviser, or technically curious grower who needs to compare a baseline and a candidate strategy before a physical trial.

Direct real-greenhouse control, safety alarms, yield or profit guarantees, and black-box autonomous optimization remain out of scope. They require greenhouse-specific calibration, live sensor validation, hardware integration, fail-safe engineering, domain supervision, and clear accountability.

The detailed evidence, users, promise, boundaries, success measures, and staged roadmap were added to PRODUCT_STRATEGY.md.

Completed implementation

  • A result can be saved as a versioned baseline after at least one model step. It remains available through local browser storage, with an in-memory fallback when storage is unavailable.
  • A reset receives a new run identifier. Numeric deltas remain hidden until baseline and candidate are separate runs using the same model engine and exactly the same model-step horizon.
  • Different weather scenarios are allowed for broad scenario exploration but produce a visible warning that weather and control effects are combined.
  • Both runs show scenario, step, control mode, engine, and either automatic targets or all six manual actuator settings.
  • The comparison reports heating, supplemental lighting, CO₂, estimated cost, fruit dry mass, and end-state climate alerts.
  • Colour is not the only signal, and the interface states that favourable resource or crop direction is not an overall winner and is not production advice.
  • The feature is fully bilingual, responsive, keyboard-operable, and uses polite live status messages.
  • Stylesheet and script cache-busting identifiers were updated so an already-open local browser receives this iteration.

Known limitations and next evidence

  • The comparison has static contracts and live-delivery checks but still needs one real browser interaction and visual review when browser control is available.
  • The fixed cost assumptions need visible provenance and configurable tariff and carbon-intensity scenarios.
  • A reproducible experiment recipe and reviewable report should precede more optimization features.
  • Uncertainty and sensitivity ranges are more valuable than presenting additional deterministic point estimates.
  • Sensor import and greenhouse-specific calibration are required before describing the product as a live digital twin.
  • The repository owner must choose a software license before broad reuse is invited.
